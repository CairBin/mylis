# 裸机 / 自定义分配器契约

`mylgc` 不自己调用 `malloc/free`，所有内存都经两个回调取得：

```c
void myrt_gc_backend_set_allocator(void* (*alloc)(size_t), void (*free)(void*));
```

宿主（libc、RTOS、裸机适配层）负责提供这两个函数。GC 只保证“申请多少、何时释放”，
不假设分配器来自操作系统，也不要求把内存归还给 OS。

## 1. 必须满足的语义

| 要求 | 说明 |
| --- | --- |
| `alloc(n)` 返回 16 字节对齐、可读写、至少 `n` 字节的块 | GC 的块头按 8/16 字节访问；不对齐会直接崩溃 |
| `alloc` 失败返回 `NULL` | GC 会把本次分配当成 OOM，不继续写 |
| `free(p)` 必须把块还回可复用池 | **“可回收”指池内可再次分配，不是还给 OS** |
| `free` 接受 GC 传回的任意块 | 块可能来自对象堆、页表桶、入口池、工作队列，大小从几十字节到数 MB |
| `free(NULL)` 可安全忽略 | 防御性要求 |
| 单线程调用 | 运行时语言层无线程；分配器不需要加锁 |
| 不得重复释放同一块 | GC 不会重复 free，但分配器自身要能发现明显的双 free 更好 |

只要 `free` 真正可复用，GC 的动态缩容就是安全的：堆变小时，超过需求 4 倍的桶数组、
入口池会被 free，下一轮增长再 alloc。反之，如果 `free` 是空实现，GC 仍能正确回收对象，
但**元数据会随每次缩容累积**，长期运行会吃光池子。

## 2. 为什么 bump 分配器不够

裸机上最容易写的是：

```c
static unsigned char pool[SIZE];
static size_t top;
void *alloc(size_t n) { void *p = pool + top; top += n; return p; }
void  free(void *p)  { (void)p; }
```

它只能向前走。GC 清扫掉的死对象、缩容掉的旧页表都不会被再次使用，`top` 单调上升，
最终 OOM。**这不满足本契约**，只能用于“一次性跑完就复位”的极端场景。

## 3. 最小可用实现

单线程下，一个带块头和空闲链的 first-fit 分配器即可：

```c
typedef struct Hdr {
    size_t size;          // 本块总大小（含 Hdr）
    struct Hdr *next;     // 空闲链
} Hdr;

static unsigned char pool[32 * 1024 * 1024];
static size_t brk;
static Hdr *free_list;

void *arena_alloc(size_t n) {
    n = (n + 15) & ~(size_t)15;          // 16 字节对齐
    size_t need = sizeof(Hdr) + n;

    Hdr **pp = &free_list;
    while (*pp) {
        Hdr *h = *pp;
        if (h->size >= need) {
            size_t left = h->size - need;
            if (left >= sizeof(Hdr) + 16) {  // 切分
                Hdr *rest = (Hdr *)((char *)h + need);
                rest->size = left;
                rest->next = h->next;
                *pp = rest;
            } else {
                *pp = h->next;               // 整块给出
            }
            return (char *)h + sizeof(Hdr);
        }
        pp = &h->next;
    }

    if (brk + need > sizeof(pool)) return NULL;
    Hdr *h = (Hdr *)(pool + brk);
    brk += need;
    h->size = need;
    return (char *)h + sizeof(Hdr);
}

void arena_free(void *p) {
    if (!p) return;
    Hdr *h = (Hdr *)((char *)p - sizeof(Hdr));
    h->next = free_list;
    free_list = h;
}
```

要点：

- 头放在返回指针之前，`free` 用固定偏移找回；
- 申请大小按 16 字节向上取整；
- 大块可以切分，剩余部分留在空闲链；
- 至少实现 free-list；进一步可做相邻块合并（coalesce）降低碎片；
- 池大小建议 ≥ 存活对象峰值 + 4–8MB 元数据余量；元数据峰值与堆块数相关
  （页表约每块 3 个入口，桶数约 2×块数）。

## 4. GC 会申请什么

| 用途 | 生命周期 | 大小特征 |
| --- | --- | --- |
| 对象块 / 大字符串 | 存活期由程序决定，清扫后 free | 8B 到数 MB |
| 页表桶数组 | 每次重建按堆大小分配，缩容时 free | 1024–8192 个指针 |
| 页表入口池 | 每块可跨页多入口，缩容时 free | 数万入口 |
| 工作队列 | 标记期间扩容 | 根/栈字数级别 |

所以分配器不能只支持固定小对象，也不能假设“free 后不会再有大块请求”。

## 5. 已验证

用上面的空闲链 arena（32MB 池）跑 30 万次分配 + 1000 个根：

```
arena-free-ok high=1331KB
```

同样的负载在 no-op free 的 arena 下会累积到 26MB。说明在满足本契约时，
GC 的页表缩容和对象清扫都能被真正复用，不会随回收轮次线性增长。

## 6. 接入位置

- 裸机运行时：在 `myrt` 的 freestanding 适配层里实现 `arena_alloc/arena_free`，
  启动时调用 `myrt_gc_backend_set_allocator`；
- GC 本体（`mylgc`）不包含具体分配器，也不依赖 libc；
- 如果目标平台已有 RTOS 堆，直接转发到 RTOS 的 `malloc/free` 即可，只要它满足上表。
