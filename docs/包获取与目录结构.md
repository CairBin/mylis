# 包获取与目录结构

本文描述 Mylis 当前实现的包来源、拉取过程、本地导入方式、缓存/工程目录，以及编译后产生的文件和目录。  
结论以当前 `mylc` 代码为准，不描述尚未实现的包管理能力。

> **关于 `dist/`**：本文中的 `dist/` 只是“发布产物目录”的示例名字，不是 Mylis 规范、`mylc` 也不要求或自动创建它。你可以把它换成 `vendor/`、`libs/`、`release/` 或任意目录；真正有意义的是 `mylis.toml` 里 `mylib = "..."` 指向的文件路径。`build/` 才是 `mylc build` 的默认构建输出目录，`dist/` 通常是人工整理后用于分发的目录，两者不是一回事。

---

## 1. 总览

当前支持五类依赖：

| 来源 | 清单写法 | 获取方式 | 是否有源码 | 典型用途 |
|---|---|---|---|---|
| 本地源码包 | `path = "../Foo"` | 直接读本地目录 | 有 | 同仓/同机开发、std 源码包 |
| Git 源码包 | `git = "..."` + `tag`/`rev`/`branch` | 裸仓库克隆 + checkout | 有 | 远程源码依赖 |
| 本地 `.mylib` | `mylib = "../Foo.mylib"` | 直接读归档 | 无（只有 API/MIR） | 预编译 MIR 库 |
| HTTP(S) `.mylib` | `mylib = "https://..."` | `curl` 下载到缓存 | 无 | 远程预编译库 |
| 本地 registry | `version = "..."` + 可选 `registry` | 读本地 registry 目录 | 有 | 本地版本仓库 |

**当前不支持**：

- HTTP(S) 直接下发源码包或源码 tarball；远程源码请用 Git。
- 远程 registry 服务；registry 是一个本地目录。
- Git 仓库内再套 workspace 子包；Git 包的 `mylis.toml` 必须位于仓库根目录。

## 2. 本地源码包

### 2.1 清单写法

```toml
[dependencies]
Foo = { path = "../Foo" }
# 也支持简写
Bar = "../Bar"
```

`path` 相对当前 `mylis.toml` 所在目录解析，不是相对当前工作目录。

### 2.2 包目录要求

```text
Foo/
├── mylis.toml              # 必需
├── src/
│   ├── lib.myl             # 默认库入口；也可由 [lib].entry 指定
│   ├── vector.myl          # import "Foo/vector" 的子模块
│   └── ...
├── lib/                    # 可选，[build].paths 的额外搜索根
└── build/                  # 可选，构建产物
```

`mylis.toml` 最小示例：

```toml
[package]
name = "Foo"
version = "1.0.0"

[lib]
entry = "src/lib.myl"

[dependencies]
Bar = { path = "../Bar" }
```

- `name` 必须和消费方依赖键完全一致，否则报“依赖名不匹配”。
- 没有 `[lib].entry` 时，包根 API 默认找 `src/lib.myl`。
- `[build].paths` 缺省为 `["src", "lib"]`，用于该包源码的模块搜索根。
- `[targets.*]` 不写时，若声明了 `[lib] entry`，`mylc build` 会合成一个静态库目标。

### 2.3 解析过程

1. `walk_graph` 以当前 manifest 目录为基准，`canonical(base.join(path))` 得到包根。
2. 读取 `<包根>/mylis.toml`，校验包名、版本。
3. 递归处理 `manifest.dependencies`；同一包名只允许一个源/版本。
4. 计算源码包 checksum：包内所有 `.myl` 和 `mylis.toml` 按相对路径排序后，对“相对路径 + 文件内容”做 SHA-256；`build/`、`target/`、`.git/` 不参与。
5. 结果写入根工程的 `mylis.lock`（首次生成或 `--update-lock`）。
6. 编译时直接使用包根，不把源码复制进消费方工程。

### 2.4 源码 import 规则

消费方：

```myl
import "Foo";          // Foo/src/lib.myl（或 [lib].entry）
import "Foo/vector";   // Foo/src/vector.myl，失败后尝试 Foo/vector.myl
```

包根 API 的模块名/路径由 `program::Loader` 按包根计算；`src/` 前缀会被去掉，`lib.myl` 视为包根模块。

### 2.5 源码包产物

源码包本身不单独产出 `.a`/`.so`；它被编译进消费方的目标。

消费方 `mylc build` 后：

```text
consumer/
├── mylis.toml
├── mylis.lock
├── src/
└── build/
    ├── app                 # 默认 out = build/<target>
    ├── app.myl.c           # MIR-C 中间源码；LLVM 后端为 app.myl.ll
    └── ...
```

如果消费方目标有 `out`，则按 `out` 指定；不会自动加 `lib` 前缀或扩展名。

## 3. Git 源码包

### 3.1 清单写法

```toml
[dependencies]
Foo = { git = "https://example.com/Foo.git", tag = "v1.0.0" }
# 或
Foo = { git = "https://example.com/Foo.git", rev = "abc1234" }
Foo = { git = "https://example.com/Foo.git", branch = "main" }
```

`git` 支持 Git 本身支持的 URL（HTTPS/SSH 等）。`tag` / `rev` / `branch` 三选一；都没有时按 `HEAD`。

### 3.2 缓存目录

默认：

```text
${HOME}/.mylis/git/
├── db/
│   └── <url-hash-16>/              # bare 仓库
└── checkouts/
    └── <url-hash-16>/
        └── <commit>/               # detached worktree
            ├── mylis.toml
            ├── src/
            └── ...
```

- `<url-hash-16>` = `sha256(git URL)` 的前 16 个字符。
- 可用 `MYLIS_GIT_CACHE` 覆盖 `~/.mylis/git`。
- checkout 不修改 bare 仓库，使用 `git worktree add --detach`。

### 3.3 拉取过程

1. 首次：`git clone --bare --quiet <url> db/<url-hash-16>`。
2. 已有 bare 仓库且非离线：`git fetch --quiet --tags --force origin`。
3. 有锁文件 pin 时，直接使用锁里的 commit；否则对 `rev`/`tag`/`branch`/`HEAD` 执行 `rev-parse <spec>^{commit}`。
4. 若 `checkouts/<url-hash-16>/<commit>/mylis.toml` 不存在，则 `git worktree add --detach` 创建。
5. 读取 checkout 根目录的 `mylis.toml`，校验包名，递归处理其依赖。
6. 计算源码 checksum，写入消费方根工程的 `mylis.lock`。
7. 离线模式下不 clone、不 fetch；缓存不存在直接报错。

### 3.4 Git 包目录要求

Git 包目录 = checkout 根：

```text
<checkout>/
├── mylis.toml
├── src/
│   ├── lib.myl
│   └── ...
└── ...
```

`mylis.toml` 必须在仓库根；当前不扫描 `packages/foo/mylis.toml` 这类 workspace 子目录。

### 3.5 锁文件记录

Git 依赖在 `mylis.lock` 中记录：

```toml
[[package]]
name = "Foo"
version = "1.0.0"
source = "git+https://example.com/Foo.git#<commit>"
checksum = "sha256-..."
```

后续编译若锁文件的 source/version/checksum 与当前 checkout 不一致，会要求运行 `mylc --update-lock`。

## 4. 本地 `.mylib`

`.mylib` 是预编译 MIR 归档，不是源码包；消费方只拿到 API 声明和 MIR（可能还有 native 载荷）。

### 4.1 清单写法

```toml
[dependencies]
Foo = { mylib = "../dist/Foo.mylib" }
# 可选外部文件 checksum
Bar = { mylib = "../dist/Bar.mylib", checksum = "sha256-..." }
```

也支持：

```toml
Foo = { mylib = "file:///absolute/path/Foo.mylib" }
```

- 相对路径相对 `mylis.toml` 所在目录。
- `mylib` 文件名不必等于包名，但归档头部的 `name` 必须等于依赖键（`Foo`）。
- `checksum` 是**整个 `.mylib` 文件**的 SHA-256；不是归档内部 body checksum。
- 归档内部 `mylib::read` 还会校验 `body` checksum。

### 4.2 目录要求

最小只需要一个文件。下面的 `dist/` 只是示例目录，不是必须叫 `dist`：

```text
dist/
└── Foo.mylib
```

真正的要求是：

- `mylis.toml` 里的 `mylib` 路径指向这个文件；
- 归档头部的 `name` 与依赖键一致；
- 如果使用相对路径，路径相对 `mylis.toml` 所在目录。

例如把文件放在 `vendor/Foo.mylib`，清单就写 `mylib = "../vendor/Foo.mylib"`；`dist/` 本身没有特殊含义。

如果 `.mylib` 没有嵌入 native，而它依赖外部 C 库，则需要额外交付：

```text
dist/
├── Foo.mylib
├── include/foo.h          # Foo 的 @header API 需要
└── lib/
    ├── libfoo.a
    └── libfoo.so          # 或 Windows .lib/.dll/.dll.a
```

`.mylib` 本身不负责复制这些 sidecar 库；消费方通过 `[native]` 或命令行链接；Windows MSVC 侧车是 `.lib`，MinGW 是 `.a` / `.dll.a`。

### 4.3 解析过程

1. 读取 `mylib` 路径；相对路径按 manifest 目录解析。
2. 计算整个归档文件的 SHA-256；若清单有 `checksum` 则比对。
3. `mylib::read` 校验归档 body checksum、解析 `api` / `apis` / `mir` / `deps` / native 段。
4. 校验 `lib.name == dep.name`。
5. 生成虚拟 API 模块路径：
   ```text
   <消费方项目根>/.mylib/Foo/lib.myl
   <消费方项目根>/.mylib/Foo/<子模块>.myl
   ```
   这些路径是 `Loader::load_virtual` 的模块键，通常不实际落盘。
6. 递归解析 `.mylib` 的 `--- deps` 中 `mylib+...` 依赖（`--link-mylib` 路径已实现；包清单里的 `.mylib` 传递依赖见“限制”）。
7. 编译时把 API 注入语义分析，把 MIR 合并进最终可执行文件。

### 4.4 消费方 import

```myl
import "Foo";          // 根 API
import "Foo/vector";   // 子模块 API
```

`.mylib` 的根 API 段名是 `lib`，但消费方看到的包名是归档 `name`；子模块路径由归档 `apis` 段标签决定。

### 4.5 锁文件记录

```toml
[[package]]
name = "Foo"
version = "1.0.0"
source = "mylib+../dist/Foo.mylib"
checksum = "sha256-<整个归档文件>"
```

锁文件不记录 native sidecar 的路径或链接参数。

### 4.5.1 std 平台后端的自动选择：`--std`

`mylc` 与 `mylc build/run` 提供 `--std`，用于把标准库源码和当前平台的 native 侧车一起接入：

```bash
mylc --std src/main.myl -o build/app
mylc build --std
```

入口源码出现 `"std/..."` 导入，或工程清单依赖 `std`（含本地 `path` 依赖的递归检查）时会自动启用。自动触发不检查 registry/git/mylib 远程依赖；直接 `import ... from "Path.myl"` 并用 `-I std/src` 的工程需要显式 `--std`。

查找顺序：

1. `MYLIS_STD_ROOT` 指向的 `std` 包根（必须含 `mylis.toml`）
2. 从当前目录向上找 `std/mylis.toml`
3. 编译器可执行文件向上最多 4 层的 `std/mylis.toml`

找到后自动加入：

- `std/src` 作为 Mylis 模块搜索根
- 工程根，供 std 的 `core/...` 引用
- POSIX 平台下的 `std-posix/native` 头文件路径；Windows 下的 `std-win32/native`
- POSIX 下已存在的 `build/std-posix/native/libmylis_file.a`、`libmylis_io.a`、`libmylis_time.a`、`libmylis_net.a`、`libmylis_event.a`、`libmylis_process.a`
- Windows MSVC 下已存在的 `build/std-win32/native/mylis_file.lib`、`mylis_io.lib`、`mylis_time.lib`、`mylis_net.lib`、`mylis_event.lib`、`mylis_process.lib`
- Windows MinGW 下已存在的 `build/std-win32/native/libmylis_file.a`、`libmylis_io.a`、`libmylis_time.a`、`libmylis_net.a`、`libmylis_event.a`、`libmylis_process.a`

边界：

- `--std` 既可显式传入，也会在入口源码出现 `"std/..."`、或清单依赖 `std` 时自动启用；本地 `path` 依赖会被递归检查（最多 8 层），registry/git/mylib 远程依赖不会。
- 它只选择**当前编译器所在平台/ABI**的侧车：POSIX 选择 `std-posix`；Windows 选择 `std-win32`，再按 `mylc` 的 MSVC/MinGW ABI 选 `.lib` 或 `.a`。
- native 仍是非嵌入的；`--std` 只是把已构建的 `.a`/`.lib` 加进链接，不会把 native 库塞进 `.mylib`。
- 显式 `-I` / `--link` 仍可叠加，重复路径会去重。

### 4.6 非嵌入 native 的查找规则

如果 `.mylib` 没有用 `--embed-static` / `--embed-shared`，归档里只有 API/MIR，没有 native 字节。  
**`mylc` 不会自动去 `.mylib` 同目录寻找 `.a` / `.so` / `.dll`。**

链接器需要的路径和库名，完全来自消费方显式输入：

| 配置/参数 | 作用 |
|---|---|
| `[native] files` / `--link <file>` | 精确指定 `.a` / `.o` / `.so` / `.dll` / `.lib` |
| `[native] dirs` / `-L <dir>` | 加入链接器的库搜索目录 |
| `[native] libs` / `-l <name>` | 按库名让链接器在 `-L` 和系统默认目录中查找 |
| `[native] include` / `-I <dir>` | 加入 C 头文件搜索路径；也作为 Mylis 模块搜索根，可写多条 |

例如：

```text
project/
├── mylis.toml
├── vendor/
│   ├── Foo.mylib
│   ├── include/
│   │   └── foo.h
│   └── lib/
│       ├── libfoo.a
│       └── libbar.so
```

```toml
[dependencies]
Foo = { mylib = "vendor/Foo.mylib" }

[native]
include = ["vendor/include"]
files = ["vendor/lib/libfoo.a"]
dirs = ["vendor/lib"]
libs = ["bar"]
```

这里：

- `include` 把 `vendor/include/` 加进 C 编译器的头文件搜索路径，同时加入 Mylis 模块搜索根；
- `files` 直接把 `vendor/lib/libfoo.a` 传给链接器；
- `dirs` 让链接器在 `vendor/lib` 中搜索；
- `libs` 让链接器查找 `libbar.so`（Linux）或对应平台的 `bar` 库；
- 相对路径都相对根 `mylis.toml` 所在目录。

关键限制：

- 当前 `[native]` 只读取**根包**的配置；依赖包的 `[native]` 不会自动传递给消费方。
- `.mylib` 的 `native_target` / `native_abi` 只做 ABI 校验，不包含 sidecar 的路径。
- `.mylib` 的 `--- deps` 只用于 `.mylib` 传递依赖，不记录 `.a/.so` 的路径。
- 非嵌入静态库会被链接进最终可执行文件或动态库；非嵌入动态库只在链接期找到，运行时仍需 `LD_LIBRARY_PATH`、`rpath`、`PATH` 或同目录部署。
- `mylc --shared` 不会自动把依赖的 `.so/.dll` 复制到输出目录。
- 如果希望 `.mylib` 自带 native，用 `--embed-static` / `--embed-shared`；此时消费方才走缓存提取和自动链接路径。

### 4.7 `A.mylib` + `a.so`：B 必须显式链接

如果 `A.mylib` 是**非嵌入**的，那么 `A.mylib` 里没有 `a.so` 的字节，也没有 `a.so` 的路径/链接参数。  
B 编译时虽然能通过 `A.mylib` 获得 A 的 API/MIR，但链接器仍不知道 `a.so` 在哪里。

所以 B 需要显式写：

```text
B/
├── mylis.toml
├── src/main.myl
├── vendor/
│   └── A.mylib
└── native/
    └── a.so
```

```toml
[dependencies]
A = { mylib = "vendor/A.mylib" }

[native]
files = ["native/a.so"]
```

或者用命令行：

```bash
mylc src/main.myl --link-mylib vendor/A.mylib --link native/a.so -o build/app
```

- `files` / `--link` 直接把 `a.so` 交给链接器；它是精确文件路径。
- 如果要用 `-l`，则同时写 `dirs` / `-L`，例如 `dirs = ["native"]`、`libs = ["a"]`。
- 如果 `a.so` 自己还依赖 `b.so`，B 仍要显式提供 `b.so`；`.mylib` 不会自动展开 native 的传递依赖。
- 链接成功不代表运行成功：`a.so`、`b.so` 运行时还需要 `LD_LIBRARY_PATH`、`rpath`、`PATH` 或同目录部署。

如果 A 的 native 是嵌入的：

```bash
mylc A/src/lib.myl --emit-mylib A.mylib --embed-shared a.so
```

那么 B 只需要 `A = { mylib = "A.mylib" }`，`mylc` 会提取 A.mylib 里的 native 载荷并自动加入链接；但这也是 ABI 相关的，且运行时仍要能找到 `a.so`。

如果 B 自己再产出 `B.mylib`：

- B.mylib 默认不会携带 `a.so` 的链接参数；
- C 使用 B.mylib 时仍要显式提供 `a.so`；
- 只有把 native 嵌进 B.mylib，才会走自动提取，但当前 `has_native()` 为真时会跳过 B 的 MIR 合并，不适合 B 本身还有 Mylis 实现的情况。

### 4.8 `a.so -> A.mylib -> B.mylib -> C`

结论先说：

- **C 必须显式提供 `a.so`**：非嵌入的 `.mylib` 不携带 native，也不记录 native 路径。
- **C 是否要显式提供 `A.mylib`，取决于 C 怎么链接 B.mylib**。

#### 情况一：C 用 `--link-mylib B.mylib`

如果 B.mylib 的 `--- deps` 里记录的是：

```text
dep = "A|0.1.0|mylib+../A.mylib|sha256-..."
```

那么 `mylc` 会递归读取 A.mylib，C **不需要**再写 `--link-mylib A.mylib`：

```bash
mylc src/main.myl --link-mylib vendor/B.mylib --link native/a.so -o build/app
```

但 `a.so` 仍要写 `--link`，因为 native 依赖不在这个递归里。

#### 情况二：C 用清单 `[dependencies]`

```toml
[dependencies]
B = { mylib = "vendor/B.mylib" }
```

当前实现下，包图只把 B.mylib 作为一个 `.mylib` 包，**不会展开 B.mylib 内部的 `--- deps`**。  
所以 C 还要显式加 A.mylib：

```toml
[dependencies]
B = { mylib = "vendor/B.mylib" }
A = { mylib = "vendor/A.mylib" }

[native]
files = ["native/a.so"]
```

这属于当前“包清单里的 `.mylib` 传递依赖尚未完全接入”的限制，不是设计上要求 C 永远写 A。

#### 情况三：B 构建时 A 是源码包

如果 B.mylib 的依赖来源是 `path+...`、`git+...` 或 `registry+...`，而不是 `mylib+...`，`expand_mylib_dependencies` 不会递归处理它们。  
C 需要显式提供 A 的源码包或 A.mylib，具体取决于 B.mylib 生成时链接的是哪一种。

#### 如果 a.so 被嵌入

- A.mylib 嵌入了 a.so：C 只要链接 A.mylib，`mylc` 会提取并自动链接 a.so；C 不再单独写 a.so。
- B.mylib 嵌入 a.so：C 链接 B.mylib 会自动链接 a.so，但当前 `has_native()` 为真会跳过 B 的 MIR 合并；如果 B 自己还有 Mylis 实现，不适合这样做。

### 4.9 网络来源：C 要不要再写 A

先看 B 是**源码包**还是 **`.mylib`**，两者结论不同。

| B 的来源/形态 | C 的清单是否要写 A | 原因 |
|---|---|---|
| B 是 Git 源码包 | 不需要 | C 只写 B，`walk_graph` 会读 B 的 `mylis.toml`，递归解析 A |
| B 是 registry 源码包 | 不需要 | 同上，B 的 manifest 依赖会继续展开 |
| B 是 HTTP(S) `.mylib` | 需要 | 当前 `resolve_mylib` 把 B 当成单包，不会展开 B.mylib 的 `--- deps` |
| B 是本地 `.mylib` | 需要（清单方式） | 同上 |
| B 是 `.mylib`，C 用 `--link-mylib` | 看 A 的来源 | 只有 B 的 dep 写成 `mylib+本地路径` 才会递归展开 |

#### B 是 Git 源码包

C 只写：

```toml
[dependencies]
B = { git = "https://example.com/B.git", tag = "v0.1.0" }
```

B 的 `mylis.toml` 里写：

```toml
[dependencies]
A = { git = "https://example.com/A.git", tag = "v0.1.0" }
```

C 不需要再写 A；A 会作为 B 的依赖被解析，C 的 `mylis.lock` 里会同时出现 A 和 B。

#### B 是 HTTP(S) `.mylib`

C 只写 B 不够：

```toml
[dependencies]
B = { mylib = "https://example.com/B.mylib" }
```

当前不会自动读取 B.mylib 的 `--- deps`，所以 C 还要显式写 A：

```toml
[dependencies]
B = { mylib = "https://example.com/B.mylib" }
A = { mylib = "https://example.com/A.mylib" }
```

如果 A 是源码包，也可以写 A 的 Git/path 依赖，取决于 A 实际以什么形式发布。

#### B 是 `.mylib`，用 `--link-mylib`

```bash
mylc src/main.myl   --link-mylib cache/B.mylib   --link-mylib cache/A.mylib   -o build/app
```

只有 B.mylib 的 `--- deps` 是 `mylib+../A.mylib` 这种本地路径时，`mylc` 才会自动加载 A。  
如果 A 是 HTTP(S) `.mylib` 或 `git+...`，当前不会自动下载/解析，C 仍要显式提供 A。

#### 源码包不传递 native 动态链接

“C 不写 A”只适用于 **Mylis 源码包依赖**，不适用于 native 动态库/静态库。

如果 B 是源码包，但 B 的实现依赖 `a.so`：

- B 的 `[native] libs` / `dirs` / `files` **不会自动传给 C**；
- 当前只有根包 C 的 `[native]` 会进入最终链接；
- C 仍要显式写 `a.so`，或者写 `dirs + libs`：

```toml
# C/mylis.toml
[native]
files = ["native/a.so"]
# 或
# dirs = ["native"]
# libs = ["a"]
```

链接期找到 `a.so` 只是第一步；运行期还需要 `LD_LIBRARY_PATH`、`rpath`、`PATH` 或把 `a.so` 放到可搜索目录。`mylc` 不会自动复制动态库到输出目录。

只有把 native 嵌进 `.mylib`（`--embed-static` / `--embed-shared`）才会走自动提取和自动链接；源码包没有这个“嵌入”形态。

### 4.10 最终链接者原则

非嵌入 native 的链接参数**不随依赖传递**。谁执行最终链接，谁就要在自己的根清单或命令行里提供这些参数。

| 最终构建者 | 非嵌入 `a.so` / `a.a` 写在哪 |
|---|---|
| C 构建可执行文件 | C 根 `mylis.toml` 的 `[native]`，或 `mylc` 命令行 |
| C 构建 `.so` / `.dll` | C 根 `mylis.toml` 的 `[native]`，或 `mylc` 命令行 |
| C 只构建 `.mylib` | 不发生最终链接；C.mylib 的使用者负责写 |
| B 是源码包且自己的 `[native]` 写了 a.so | 仍要 C 写；B 的 `[native]` 不会传播 |
| A.mylib / B.mylib 非嵌入 | 仍要 C 写；归档里没有 native 路径 |

所以不能依赖：

```text
a.so -> A.mylib -> B.mylib -> C
```

自动把 `a.so` 一路传到 C。C 必须显式写：

```toml
[native]
files = ["native/a.so"]
```

`[native]` 只读取根包，不读取依赖包的配置。命令行 `--link` / `-L` / `-l` 是等价的显式输入，也可以代替根清单。

例外只有：

- `.mylib` 用 `--embed-static` / `--embed-shared` 嵌入了 native；
- native 是运行时 `system_libs` 里已经存在的系统库（如 `m`、`pthread`、`ws2_32`），不是任意第三方 `a.so`。

### 4.11 头文件怎么收集

当前 `mylc` **不自动收集依赖包的头文件**。它只为当前正在构建的 C 库生成一个自己的 `.h`。

#### 什么时候生成头文件

只有构建静态库/动态库时：

```bash
mylc src/lib.myl --static  -o dist/libfoo.a
mylc src/lib.myl --shared  -o dist/libfoo.so
```

输出旁边会生成同名头文件：

```text
dist/
├── libfoo.a       # 或 libfoo.so / libfoo.dll
└── libfoo.h
```

`mylc build` 的静态库/动态库目标也一样，例如输出 `build/libfoo.a`，头文件是 `build/libfoo.h`。

头文件内容：

- 只列出带 `@export` 的顶层函数；
- 生成 `<入口文件名>_init()` 初始化函数；
- 只包含 `<stdint.h>` / `<stdbool.h>` / `<stddef.h>`，不依赖 `mylrt.h`；
- 字符串是 `typedef struct MyStr MyStr;`；
- 导出签名用到的类、枚举等做不透明声明。

#### 什么时候不生成头文件

- `mylc --emit-mylib` 只生成 `.mylib`，不生成 `.h`；
- 普通可执行文件不生成公共头；
- 纯 MIR 的 `.mylib` 不生成公共头，也没有 C 头可收集。

#### 依赖的头文件不会自动收集

- `.mylib` 里没有头文件；它只有 API/MIR；
- 依赖包的 `.h` 不会被复制到消费方构建目录；
- `mylis.toml [native]` 支持 `include` / `files` / `dirs` / `libs`；`include` 可声明多个头文件根；
- `mylc -I` 现在**同时**作为 Mylis 模块搜索路径和 C 头文件搜索路径（MIR/AST/C 编译阶段会转发）；
- 如果 A 库有 `A.h`，B 或最终消费者要自己把 `A.h` 放到发布目录，并在根清单 `[native] include` 或 `-I` 中指定。

#### C 消费方怎么用

```bash
cc app.c -I dist -L dist -lfoo -o app
```

发布目录应同时包含：

```text
dist/
├── libfoo.a
├── libfoo.so      # 如果用动态库
└── libfoo.h
```

如果消费方是 Mylis 项目而不是 C 项目，则不需要 C 头文件，直接用 `.mylib` 的 API/MIR。

#### 当前边界

目前没有“包内自动收集头文件”的机制，也没有自动扫描 `include/` 的约定。头文件分发仍是发布者手工整理；与 `cflags` 里的相对 `-I` 不同，`[native] include` 的相对路径以 `mylis.toml` 所在目录为基准，并且会被转发给 C 编译器。

### 4.12 Mylis 引用 C 时怎么找头文件

`@header("foo.h")` 本身不负责找文件；它只是让 C 后端在生成的 C 代码里写：

```c
#include <foo.h>
```

真正的查找由 C 编译器完成。

#### 查找顺序

C 编译器按自己的规则搜索：

1. `mylc` 总是加的两个运行时目录：
   - `myrt/`（`mylrt.h`）
   - `gc/include/`（`mylrt_gc.h`）
2. 工具链的 `cflags` 里的 `-I`；
3. 根清单 `[native] include` 和命令行 `-I` 目录；
4. C 编译器自己的系统 include 目录；
5. 都没有就报 `fatal error: foo.h: No such file or directory`。

`mylc` 不会按 `mylis.toml` 所在目录自动拼 `include/`，也不会去依赖包目录里找头文件；需要显式写 `[native] include`。

#### 自定义头文件的路径怎么写

在根工程的 `mylis.toml` 里加：

```toml
[native]
include = ["include", "vendor/foo/include"]
```

相对路径以 `mylis.toml` 所在目录为基准。也可以继续用工具链 `cflags`：

```toml
[toolchain]
cflags = ["-Iinclude", "-Ivendor/foo/include"]
```

或者用命令行 / 环境变量：

```bash
mylc src/main.myl -Iinclude -Ivendor/foo/include
MYLIS_CFLAGS="-I/path/to/include" mylc src/main.myl
```

绑定文件里写：

```mylis
@header("foo.h")
pub unsafe fn foo(x: i32) -> i32;
```

生成 C 后就是 `#include <foo.h>`，再由上面的 `-I` 找到。

注意：

- `mylc -I` 现在**同时**作为 Mylis 模块搜索路径和 C 头文件搜索路径；MIR/AST/C 编译阶段会把它转发给 C 编译器（MSVC 或 MinGW）；
- `[native] include` 等价于追加 `-I`，但相对路径以 `mylis.toml` 所在目录为基准；同时接受 `includes` 别名；
- `[build].paths` 只是 Mylis 模块搜索根，不是 C 头路径；
- `cflags` 里的相对 `-I` 是相对**启动 `mylc` 的当前目录**，不是相对 `mylis.toml`；不确定时用绝对路径，或在工程根目录启动。

#### 如果不写 `@header`

无体 `unsafe fn` 也可以不写 `@header`：

```mylis
pub unsafe fn foo(x: i32) -> i32;
```

这时 C 后端直接生成 `extern` 声明，不引入头文件；符号名和类型必须与 C 完全一致。头文件仍然不需要，但链接时仍要提供对应 `.a` / `.so`。

#### LLVM 后端的情况

当前默认 LLVM 后端不会为了 `@header` 去读 C 头文件；它主要按符号名生成 LLVM `declare`。  
因此“头文件查找”主要发生在 C 后端 / MIR-C 后端；LLVM 路径下更多是链接期找符号，不是编译期找头。

### 4.13 项目目录约定（建议）

这一节是**约定**，不是 `mylc` 当前强制校验的格式。`mylc` 只认 `mylis.toml`、入口和清单里的路径；目录可以改，但建议统一成下面这样。

#### 库包

```text
Foo/
├── mylis.toml
├── mylis.lock              # 可选；应用提交，库包按需
├── src/
│   ├── lib.myl             # 默认入口
│   ├── Foo_bind.myl        # @header C 绑定
│   └── vector.myl          # import "Foo/vector"
├── include/                # 对外 C 头文件
│   └── foo.h
├── native/                 # 本包自己的 native 库
│   ├── libfoo.a
│   └── libfoo.so
├── mylib/                  # 可选：预编译的 Foo.mylib
├── vendor/                 # 第三方依赖，不对外承诺
│   ├── A.mylib
│   └── native/...
├── tests/
├── examples/
├── build/                  # 生成，不提交
└── dist/                   # 发布 staging，可选
```

各目录职责：

| 目录 | 用途 | 是否提交 | 消费者怎么用 |
|---|---|---|---|
| `src/` | Mylis 源码；默认入口 `src/lib.myl` | 是 | 源码包依赖，或自己编译 |
| `include/` | **公开 C 头文件** | 是 | `-I<包>/include` |
| `native/` | 本包自己的 `.a` / `.so` / `.dll` | 视发布方式 | 根清单 `[native]` |
| `mylib/` | 本包的预编译 `.mylib` | 视发布方式 | `mylib = "..."` |
| `vendor/` | 第三方 `.mylib` / native / 头文件 | 按需 | 仍是显式路径，不自动传播 |
| `lib/` | **Mylis 额外模块搜索根** | 是 | `[build].paths` 默认包含 |
| `build/` | `mylc build` 生成物 | 否 | 不发布 |
| `dist/` | 人工整理的发布目录 | 否（作为产物） | 发布时复制/上传 |

重点：`lib/` 不是 native 库目录。`[build].paths` 默认是 `["src", "lib"]`，`lib/` 放的是 Mylis 模块源码；C 的 `.a/.so` 放 `native/`，避免和模块搜索根混在一起。

#### 消费方工程

```text
app/
├── mylis.toml
├── mylis.lock
├── src/
│   └── main.myl
├── include/                # 应用自己的 C 头
├── vendor/
│   ├── Foo.mylib
│   ├── include/
│   │   └── foo.h
│   └── lib/
│       ├── libfoo.a
│       └── libfoo.so
├── build/
└── dist/
```

```toml
[dependencies]
Foo = { mylib = "vendor/Foo.mylib" }

[native]
include = ["vendor/include"]
files = ["vendor/lib/libfoo.a"]
# 或者：
# dirs = ["vendor/lib"]
# libs = ["foo"]
```

- `vendor/` 是消费方本地固定副本，路径稳定；
- `include/` 放公开 C 头，`[native] include` 显式加入；
- `native/` 也可以作为消费方自己的 native 库目录，效果和 `vendor/lib` 一样，只是命名不同；
- `dist/` 如果用于发布，建议按 `include/`、`lib/`、`mylib/` 分开放。

#### 推荐发布结构

```text
dist/
├── include/
│   └── foo.h
├── lib/
│   ├── libfoo.a
│   └── libfoo.so
└── mylib/
    └── Foo.mylib
```

- C 消费者：`cc app.c -Idist/include -Ldist/lib -lfoo`
- Mylis 消费者：`Foo = { mylib = "dist/mylib/Foo.mylib" }`
- 非嵌入 native：还在最终链接者的根 `[native]` 里写 `dist/lib/libfoo.a` 或 `dirs + libs`

#### 跨平台 native 库

如果同一个包要放多平台库，建议：

```text
native/
├── x86_64-unknown-linux-gnu/
│   ├── libfoo.a
│   └── libfoo.so
└── x86_64-pc-windows-msvc/
    ├── foo.lib
    └── foo.dll
```

当前 `[native]` 没有按 target/ABI 自动选择的字段，必须由构建方在根清单或命令行选择对应目录。跨平台包不要把多个平台的同名库平铺在同一个 `native/` 里。

#### 当前强制与不强制

`mylc` 当前强制的只有：

- 包根有 `mylis.toml`；
- 入口和依赖路径能在清单/命令行指定；
- 非嵌入 native 在最终链接者的根 `[native]` 或命令行里出现。

`include/`、`native/`、`mylib/`、`vendor/`、`dist/` 都是约定，不是编译器自动扫描的目录。特别是：

- 不会自动把 `include/` 加进 C 编译器的 `-I`；
- 不会自动从 `native/` 找 `.a/.so`；
- 不会自动从 `vendor/` 解析依赖；
- 不会自动复制头文件或动态库到 `dist/`。

### 4.14 A、B 都带 include 时怎么放

核心规则：**公开头文件必须带包名命名空间**，不要把所有包的 `foo.h` 平铺到同一个 include 根。

#### 包内布局

A：

```text
A/
├── include/
│   └── A/
│       └── foo.h
└── src/
    └── A_bind.myl
```

B：

```text
B/
├── include/
│   └── B/
│       └── bar.h
└── src/
    ├── lib.myl
    └── B_bind.myl
```

A 的绑定：

```mylis
@header("A/foo.h")
pub unsafe fn a_foo(x: i32) -> i32;
```

B 的绑定：

```mylis
@header("A/foo.h")
pub unsafe fn b_use_a(x: i32) -> i32;

@header("B/bar.h")
pub unsafe fn b_bar(x: i32) -> i32;
```

各自构建时：

```toml
[toolchain]
cflags = ["-Iinclude"]
```

这样 `@header("A/foo.h")` 在 A 包内解析到 `A/include/A/foo.h`，`@header("B/bar.h")` 解析到 `B/include/B/bar.h`。

#### B 的公开头引用 A

如果 `B/bar.h` 需要 A 的类型或声明：

```c
#ifndef B_BAR_H
#define B_BAR_H

#include "A/foo.h"

/* B 的公开 API */
int b_bar(int x);

#endif
```

前提是 C 的 include 根里同时有 `A/foo.h` 和 `B/bar.h`。

#### C 的发布目录

推荐合并成一个公共 include 根，而不是把 A、B 的 include 目录直接都塞进 `-I`：

```text
vendor/
├── include/
│   ├── A/
│   │   └── foo.h
│   └── B/
│       └── bar.h
├── lib/
│   ├── libA.a
│   └── libB.a
└── B.mylib
```

C 编译：

```bash
cc app.c -Ivendor/include -Lvendor/lib -lB -lA -o app
```

C 的 `mylis.toml`：

```toml
[dependencies]
B = { mylib = "vendor/B.mylib" }

[native]
include = ["vendor/include"]
files = ["vendor/lib/libB.a", "vendor/lib/libA.a"]
```

这样：

- `#include "A/foo.h"` 找 `vendor/include/A/foo.h`；
- `#include "B/bar.h"` 找 `vendor/include/B/bar.h`；
- 不会因为两个包都有 `foo.h` 而互相覆盖。

#### 不合并时怎么写

如果 C 直接保留两个包的 include 根：

```toml
[toolchain]
cflags = [
  "-I../A/include",
  "-I../B/include",
]
```

这能工作，但要求头文件本身已经带包名前缀：

- A 的头是 `A/include/A/foo.h`；
- B 的头是 `B/include/B/bar.h`；
- B 里写 `#include "A/foo.h"`，通过 `-I../A/include` 找到。

如果 A 和 B 都使用裸 `foo.h`，两个 `-I` 同时加入就会产生同名覆盖，不能这样做。

#### C 是 Mylis 项目时

如果 C 只通过 B.mylib 的 Mylis API 使用 B：

- C 不需要 A、B 的 C 头文件；
- `include/` 与 `@header` 不参与；
- 只需要 `.mylib` 依赖和必要的 native 链接；
- 如果 B.mylib 依赖 A.mylib，按 4.8 / 4.9 的规则处理 A.mylib 和 native。

如果 C 的 Mylis 代码要编译 B 的源码包，而 B 的 `@header` 需要 A 的头：

- `mylc` 不会自动把 A 的 `include/` 加进 C 编译器；
- C 的根 `[toolchain] cflags` 必须显式加 `-I<A>/include`、`-I<B>/include`；
- Git 缓存的路径不稳定，发布/复现时建议把 A、B 的公开头复制到 C 的 `vendor/include`。

## 5. HTTP(S) `.mylib`

### 5.1 清单写法

```toml
[dependencies]
Foo = { mylib = "https://example.com/pkgs/Foo.mylib", checksum = "sha256-..." }
```

### 5.2 下载与缓存

默认：

```text
${HOME}/.mylis/mylib/
├── downloads/
│   └── <url-hash-16>.mylib
└── native/
    └── <payload-hash>/
        ├── libfoo.a
        └── libfoo.dll
```

- `<url-hash-16>` = `sha256(URL)` 的前 16 个字符。
- 可用 `MYLIS_MYLIB_CACHE` 覆盖 `~/.mylis/mylib`。
- 使用 `curl -fL --silent --show-error -o <dest> <url>`。
- 已存在缓存文件时不再下载；没有 HTTP 条件请求/ETag 刷新逻辑。
- 离线模式：缓存不存在直接报错，不访问网络。

### 5.3 过程和目录

1. URL 下载到 `mylib/downloads/<hash>.mylib`。
2. 对下载文件做外部 checksum（如果清单提供）。
3. `mylib::read` 校验归档内部 checksum。
4. 归档的实际根目录是缓存文件所在目录；API 仍然以消费方项目根 `.mylib/<name>/...` 作为虚拟路径。
5. 如果归档包含 native 载荷：
   - 载荷解到 `mylib/native/<payload-hash>/`；
   - 链接阶段使用该缓存路径；
   - 共享库可能使用缓存绝对路径的 rpath，发布前需要重新处理（见 `docs/std平台与异步约定.md`）。
6. 如果归档不嵌入 native：消费方必须自行提供 sidecar `.a/.so/.dll`，可通过 `[native]` 配置。

### 5.4 限制

- HTTP(S) 只用于 `.mylib`；没有 HTTP 源码包。
- 下载缓存不记录 HTTP 响应头；无 TTL、ETag、增量更新。
- 外部 checksum 为空时，只有归档内部 checksum 保护；不能验证 URL 内容来源。

## 6. 本地 registry

### 6.1 清单写法

```toml
[dependencies]
Foo = { version = "^1.2.0" }
# 命名 registry
Bar = { version = "1.0.0", registry = "local" }
```

- 不写 `path`、`git`、`mylib` 时，走 registry。
- `version` 支持 `*`、`^1.2.0`、`~1.2.0`、`=1.2.3` 等，由 `semver::Req` 解析。
- 默认 registry 目录：`${HOME}/.mylis/registry`，可用 `MYLIS_REGISTRY` 覆盖。
- 命名 registry：`MYLIS_REGISTRY_<NAME>`，名称转大写、`-` 转 `_`；`registry` 值含 `/`、`\` 或以 `.` 开头时按路径处理。

### 6.2 目录结构

```text
<registry-base>/
└── Foo/
    ├── 1.2.0/
    │   ├── mylis.toml
    │   └── src/
    │       └── lib.myl
    └── 1.3.0/
        ├── mylis.toml
        └── src/
```

- 目录名必须是可解析的 semver 版本。
- 选择满足版本约束的最高版本；有锁文件时按 pin 的版本读取。
- `mylis.toml` 的 `name` 必须等于包名。
- 源码 checksum 与 path 包相同。

### 6.3 锁文件记录

```toml
[[package]]
name = "Foo"
version = "1.2.0"
source = "registry+default@1.2.0"
checksum = "sha256-..."
```

命名 registry 的 source 形如 `registry+local@1.2.0`。

## 7. `mylis.lock` 与解析顺序

根工程：

```text
project/
├── mylis.toml
├── mylis.lock
├── src/
└── build/
```

`mylis.lock`：

- 位置：根 `mylis.toml` 同目录。
- 首次编译包或 `mylc build` 时，如果锁不存在会自动生成。
- `mylc --update-lock` 强制重新生成。
- 已有锁且未强制更新时，不静默改写。
- `source` 记录来源：
  - `path+../Foo`
  - `git+https://...#<commit>`
  - `mylib+../dist/Foo.mylib`
  - `registry+default@1.2.0`
- `checksum`：
  - 源码包：包内 `.myl` + `mylis.toml` 的组合 checksum；
  - `.mylib`：整个归档文件的 SHA-256。
- 锁不记录：
  - native 链接参数；
  - `[native] include/files/dirs/libs`；
  - 头文件搜索路径；
  - C 库 sidecar 的位置。

解析顺序（`program::Loader`）：

1. 入口文件所在目录向上找 `mylis.toml`。
2. 读取锁文件 pin（如果存在）。
3. `build_graph_with_pins_offline` 递归解析依赖。
4. 注入 `.mylib` API 虚拟模块。
5. 加载入口模块；普通 `import` 先查当前目录/搜索根，再走包图。

## 8. 编译目录与中间文件

### 8.1 单文件/命令行模式

在命令行直接给 `mylc` 一个入口文件时，默认输出到当前工作目录：

```text
cwd/
├── app                    # 可执行
├── app.myl.c              # MIR-C 中间源码
├── app.myl.ll             # LLVM 后端中间 IR
├── libfoo.a               # --static 默认名
├── libfoo.so              # --shared 默认名
└── libfoo.h               # 静态/动态库公共头
```

实际只会生成当前后端对应的 `.myl.c` 或 `.myl.ll`。

### 8.2 包模式 `mylc build`

`mylc build` 从当前目录向上找 `mylis.toml`，然后切到 manifest 所在目录：

```text
project/
├── mylis.toml
├── mylis.lock
├── src/
│   └── main.myl
└── build/
    ├── app                   # 默认 out = build/app
    ├── app.myl.ll            # 或 app.myl.c
    ├── libfoo                # kind = "static" 或 "shared"
    ├── libfoo.h
    └── libfoo.myl.ll
```

目标默认输出是 `build/<target-name>`，不会因为 `kind = "static"` 自动改成 `lib<name>.a`。要标准文件名请显式写：

```toml
[targets.libfoo]
kind = "static"
entry = "src/lib.myl"
out = "build/libfoo.a"
```

### 8.3 静态库中间文件

`kind = "static"` 时：

```text
build/libfoo.a
build/libfoo.h
build/libfoo.a.myl.c        # 后端中间源码
build/libfoo.a.o            # 编译后对象，归档完成会删除
build/libfoo.a.native.o     # 有 native 载荷合并时才出现，随后删除
```

- 公共头文件是标准 C 头，使用 `<stdint.h>` / `<stdbool.h>` / `<stddef.h>`，不依赖 `mylrt.h`。
- C 客户端如果调用 `mylrt_str_lit` 等运行时 API，需要自己额外 include `mylrt.h`。

### 8.4 动态库/可执行文件

```text
build/libfoo.so             # 或 .dll
build/libfoo.h
build/libfoo.so.myl.ll
build/app
build/app.myl.ll
```

- `.so/.dll` 不会自动把非嵌入依赖复制到输出目录。
- 嵌入 native 的 `.mylib` 共享库默认从 `~/.mylis/mylib/native/<hash>/` 链接；rpath 可能是缓存绝对路径，发布前应改为相对 `$ORIGIN` 或重新打包。

### 8.5 `.mylib` 产物

```bash
mylc Foo/src/lib.myl --emit-mylib dist/Foo.mylib
```

只生成：

```text
dist/
└── Foo.mylib
```

`.mylib` 是单文件文本归档，不生成目录；结构：

```text
MYLIB 1
abi = "mylis-1"
name = "Foo"
version = "1.0.0"
entry_stem = "lib"
decl_count = ...
checksum = "sha256-..."
native_target = "..."       # 仅 native 载荷
native_abi = "gnu"          # 仅 native 载荷
--- deps
dep = "Bar|1.0.0|mylib+../Bar.mylib|sha256-..."
--- api lib
...
--- mir
...
--- mir-json
...
--- native-static <name>
<base64>
```

- `--- deps` 是薄归档：只记录依赖元数据，不把依赖 API/MIR 复制进 Foo.mylib。
- `--embed-static` / `--embed-shared` 才把 native 载荷嵌入归档。
- 带 native 的归档会记录 `native_target` / `native_abi`，消费端按 `mylis-build.json` 校验。

## 9. 标准工程与缓存总布局

### 9.1 消费方工程

```text
app/
├── mylis.toml                # 根清单
├── mylis.lock                # 锁文件（自动生成/--update-lock）
├── src/
│   └── main.myl
├── vendor/                   # 可选：本地源码包或 .mylib
│   ├── Foo/
│   │   ├── mylis.toml
│   │   └── src/lib.myl
│   └── Bar.mylib
├── .mylib/                   # 逻辑虚拟 API 路径，通常不落盘
│   └── Bar/
│       └── lib.myl
└── build/                    # mylc build 的默认输出根
```

### 9.2 用户缓存

```text
${HOME}/.mylis/
├── git/
│   ├── db/<url-hash-16>/                       # bare 仓库
│   └── checkouts/<url-hash-16>/<commit>/      # Git 源码包 checkout
├── mylib/
│   ├── downloads/<url-hash-16>.mylib          # HTTP(S) 下载缓存
│   └── native/<payload-hash>/...              # 嵌入 native 载荷解包
└── registry/
    └── Foo/<version>/...                      # 本地 registry 源码包
```

环境变量：

| 变量 | 作用 |
|---|---|
| `MYLIS_GIT_CACHE` | 覆盖 `~/.mylis/git` |
| `MYLIS_MYLIB_CACHE` | 覆盖 `~/.mylis/mylib` |
| `MYLIS_REGISTRY` | 默认 registry 根 |
| `MYLIS_REGISTRY_<NAME>` | 命名 registry 根 |
| `MYLIS_PATH` | 额外的模块搜索根（不是包依赖） |
| `MYLIS_ROOT` | 编译器安装根 |

## 10. 当前限制与边界

1. **远程源码只支持 Git**：没有 HTTP(S) 源码 tarball / zip 下载。
2. **Git 包不支持 workspace 子目录**：`mylis.toml` 必须在 checkout 根。
3. **registry 是本地目录**：没有远程 registry 协议。
4. **HTTP(S) 只支持 `.mylib`**：下载缓存无 ETag/TTL；外部 checksum 为空时只依赖归档内部 checksum。
5. **`.mylib` 传递依赖**：
   - `--link-mylib B.mylib` 会递归解析 B 的 `mylib+...` 依赖；
   - 通过 `mylis.toml` 的 `mylib` 依赖进入包图时，传递的 `.mylib` 元数据尚未全部接入，可能需要同时声明传递归档。
6. **`.mylib` 不打包 native sidecar**：非嵌入的 `.a/.so/.dll` 由消费方通过 `[native]` 或命令行链接；Windows MSVC 侧车是 `.lib`，MinGW 是 `.a` / `.dll.a`。
7. **纯 MIR `.mylib` 不能直接导出 C 静态库/动态库**：`mylc --static/--shared` 目前拒绝纯 MIR 归档，需要嵌入 native 或改导出路径。
8. **锁文件不记录链接参数**：`mylis.lock` 只锁来源/版本/checksum；C 库路径和链接参数在 `[native]`/命令行/构建脚本中。
9. **`.mylib` 的 `native_target` / `native_abi` 可能为空**：没有 `mylis-build.json` 时无法记录并校验，只能跳过。
10. **公共 C 头只保证声明层标准 C**：字符串仍是 `MyStr*` 前置声明，调用运行时字符串函数仍需 `mylrt.h`。

## 11. 推荐使用方式

- 同仓/同机开发：用 `path` 源码包，保留源码和 manifest。
- 远程源码：用 Git + `tag`/`rev` 锁定，提交 `mylis.lock`。
- 预编译通用库：用纯 MIR `.mylib`，消费方只需要归档文件。
- 带 C 后端的平台库：用嵌入 native 的 `.mylib`，并确保 `native_target` / `native_abi` 与消费方一致。
- 需要分发非嵌入 C 库：`.mylib` + sidecar `.a/.so` + 公共头 + `[native]` 配置一起交付。
- 发布工程时提交 `mylis.toml`、`mylis.lock`；不要把 `~/.mylis` 缓存或 `build/` 中间产物当作源码交付。
